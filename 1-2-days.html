Day 1

Rendering Strategies

🎯 Why This Matters in Interviews

One of the first decisions in any system design is: where and when does HTML get generated? This affects SEO, performance, scalability, and UX. Interviewers ask it early to test architecture thinking.

The key is not just naming the strategy — it's defending it with trade-offs.
❓ The 3 Questions — Ask These Before Every Answer
1. Is this behind a login? YES → SEO irrelevant → CSR 2. Is this public and SEO critical? YES → ask next question 3. How often does content change? Never / rarely → SSG Daily / hourly → ISR Per user / real-time → SSR
⚠️ Always ask question 1 first. Skipping it is the most common mistake.
🗺️ The 4 Rendering Strategies
CSR

Client Side Rendering

Server sends empty HTML + JS. Browser runs JS and builds the page.

Example: Gmail, Slack, Dashboards behind login

✅ Rich interactions
✅ Cheap to host
❌ Blank screen until JS runs
❌ Bad SEO
SSR

Server Side Rendering

Server builds full HTML per request, sends to browser.

Example: LinkedIn profiles, public user pages

✅ Great SEO
✅ Fast First Paint
❌ Slower TTFB
❌ Higher server cost
SSG

Static Site Generation

All pages pre-built at build time and deployed to CDN.

Example: Blogs, docs, marketing sites

✅ Blazing fast (CDN)
✅ Cheapest to scale
❌ Data goes stale
❌ Slow builds at scale
ISR

Incremental Static Regen.

SSG pages with a revalidation window — rebuilt in the background.

Example: E-commerce, news articles

✅ Fast like SSG
✅ Data stays fresh
❌ Slightly stale
❌ More complex
🧭 Decision Map
Is SEO critical? ├── NO → CSR (dashboards, apps behind login) └── YES → Does content change frequently? ├── NO → SSG (blogs, docs, marketing) └── YES → Is it personalized per user? ├── YES → SSR (social feeds, profiles) └── NO → ISR (product pages, news)
💬 Weak vs Strong Interview Answer
❌ Weak: "I'd use SSR for this."
✅ Strong: "Since this is a public product page that needs SEO and the content changes maybe once a day, I'd go with ISR — CDN-level performance with a 60-second revalidation window. If the product had real-time inventory, I'd layer in a client-side fetch just for that piece."

Formula: Decision + Reason + Trade-off + Edge case awareness

🔍 Case Study — Google Autocomplete

The 6-Step Framework Applied

1

Clarify Requirements

Standalone component, 5–8 suggestions, keyboard navigation required, Google scale

2

Architecture

Search page = SSG (static, SEO critical). Suggestions = pure CSR — browser fires API calls as user types. NOT SSR.

3

Component Breakdown (Headless Pattern)

SearchPage (owns logic) → Autocomplete (dumb, generic) → SearchInput + SuggestionList → SuggestionItem

4

State — All Local (nothing global)

query, suggestions, isLoading, activeIndex. No other component needs this data.

5

Performance

Debounce (300ms) reduces API calls. AbortController fixes race conditions.

6

Accessibility

role="combobox", aria-expanded, aria-activedescendant, role="listbox", keyboard nav (arrow/enter/escape)

State design:

const [query, setQuery] = useState("") const [suggestions, setSuggestions] = useState([]) const [isLoading, setIsLoading] = useState(false) const [activeIndex, setActiveIndex] = useState(-1)

Race condition fix:

useEffect(() => { const controller = new AbortController() fetchSuggestions(query, { signal: controller.signal // cancels previous request }) return () => controller.abort() // cleanup on next keystroke }, [query])

Headless component API:

<Autocomplete query={query} suggestions={suggestions} isLoading={isLoading} onQueryChange={(val) => setQuery(val)} onSelect={(item) => handleUserSelection(item)} renderItem={(item) => <span>{item.label}</span>} // render prop />
📌 Key Concepts to Remember — Day 1
ConceptDefinition
Race ConditionWhen a slow API response from an earlier query overwrites a faster response from a later query
AbortControllerBrowser API to cancel pending fetch requests. Used to prevent race conditions
DebounceDelays API call until user stops typing for X ms. Reduces unnecessary requests
Headless ComponentComponent that owns no logic — all state/behavior passed via props. Makes it reusable for any context
Render PropA prop that accepts a function returning JSX. Allows parent to control how items render
ARIA comboboxRole for accessible autocomplete inputs. Paired with listbox/option roles for screen readers
Day 2

State Management Decision Tree

🧠 The Real Question Interviewers Are Asking
❌ Wrong framing: "Which library should I use?"
✅ Right framing: "What kind of state is this, and where should it live?"

Classify the state first. The library choice follows naturally from classification.

📦 The 4 Types of State
LOCAL STATE

Lives in one component

Nobody else needs it. Goes away when component unmounts.

Examples: dropdown open/closed, form input, modal visible

Tool: useState / useReducer

SERVER STATE

Comes from an API

Needs fetching, caching, syncing, loading/error states.

Examples: tweets list, product data, user profile

Tool: React Query / SWR

URL STATE

Lives in the browser URL

Survives page refresh. Shareable via link.

Examples: search filters, pagination, active tab

Tool: URL params / query strings

GLOBAL STATE

Multiple components need it

Pure client state. Not from API. Shared across app.

Examples: cart, theme, auth token

Tool: Zustand / Context API

🌳 State Management Decision Tree
What kind of state is this? │ ├── Only one component needs it? │ └── useState / useReducer (local) │ ├── Multiple components need it? │ ├── Is it server data (from API)? │ │ └── React Query / SWR (server state) │ │ │ ├── Should it survive refresh / be shareable? │ │ └── URL params (url state) │ │ │ └── Pure client state shared across app? │ ├── Simple? → Context API │ └── Complex? → Zustand / Jotai │ └── Real-time data (WebSockets / SSE)? └── CSR + WebSocket + useState
🔧 Each Tool — When and Why
ToolUse WhenAvoid When
useState Single value, one component Multiple related values updating together
useReducer Multiple related values, complex transitions (e.g. checkout steps) Simple single values
React Query / SWR ANY data from an API Pure client state (no API involved)
URL Params Filters, pagination, tabs — anything shareable or refreshable Sensitive flows (checkout, auth)
Context API Simple global state, infrequent updates (theme, language) Frequently changing state — causes re-renders
Zustand Complex shared client state, frequent updates (cart) Server data — use React Query instead
⚠️ Critical: User data (name, email) comes from an API — it's SERVER STATE → React Query. Not Zustand. Most candidates get this wrong.
📡 WebSocket vs SSE vs Polling
WebSocket = Bidirectional. Client AND server send messages. Best for: Chat, multiplayer games, collaborative editing. SSE = Server → Client only. One direction. Best for: Live notifications, order tracking, stock prices. Simpler than WebSocket, built for this use case. Polling = Client asks server every X seconds. Best for: Simple updates where slight delay is fine. Easiest to implement. Works everywhere.
Order tracking updates every 5 seconds → SSE, not WebSocket. No bidirectional communication needed.

⚠️ The Mistake 90% of Candidates Make
❌ Wrong thinking: "I need to store search query → put it in Redux" "I need user data → put it in Redux" "I need API results → put it in Redux" ✅ Right thinking: "Search query → only SearchBar needs it → useState" "User data → comes from API → React Query" "API results → server state → React Query, not Redux"
Redux / Zustand should only hold pure client state that multiple components truly share. API data belongs in React Query.
🗂️ Complete State Management Cheat Sheet
State type → Right tool ───────────────────────────────────────── Local UI → useState Complex local → useReducer (checkout steps, multi-value forms) Server data → React Query / SWR URL / shareable → URL params Global client → Zustand + persist Simple global → Context API Real-time 2-way → WebSocket + useState Real-time 1-way → SSE + useState Simple polling → setInterval + useState

📐 The 6-Step Framework — Use For Every Question

1

Clarify Requirements (5 min)

Who are users? What devices? What scale? What features? Any constraints?

2

High-Level Architecture (5 min)

Rendering strategy? Component tree at a high level? How does data flow?

3

Component Breakdown (10 min)

Break UI into logical components. Define APIs. Identify reusable vs one-off.

4

Data & State Management (10 min)

Classify each state. Where does it live? How is it fetched, cached, invalidated?

5

Performance (5 min)

Code splitting, image optimization, caching, CDN, Core Web Vitals.

6

Accessibility & Reliability (5 min)

Keyboard nav, ARIA, error boundaries, offline support, fallback UI.
