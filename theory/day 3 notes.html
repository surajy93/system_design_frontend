Performance Mental Model

🎯 Why This Is a Staff-Level Topic

Performance shows you think about real users on slow networks and cheap devices — and the business impact behind it.

1 second delay in page load = 7% drop in conversions. Performance is a business metric, not just a technical one.
🧱 The 4 Layers — Always Think In This Order
Layer 1 — Network

Are we sending too much?

Too much data? Too often? From too far away?
→ CDN (serve from edge) → Code splitting → Tree shaking → HTTP/2 → WebP images
Layer 2 — Parse & Run

Too much JS upfront?

Is the browser doing too much work before page is usable?
→ Lazy load heavy components → Route-based code splitting → Defer non-critical scripts → async/defer on 3rd party
Layer 3 — Render

Is painting efficient?

Is the browser doing expensive layout/paint work?
→ Virtualize long lists → CSS transforms not position → Avoid layout thrash → will-change for animations
Layer 4 — Perceived

Does it FEEL fast?

Users measure frustration, not milliseconds.
→ Skeleton screens → Optimistic updates → Progressive loading → Prefetch on hover
⚠️ Parse & Run is about JS bundle cost. NOT about SSR/CSR. That's the most common confusion.
🌐 Layer 1 — Network (Deep Dive)

Code Splitting:

❌ Everything loads upfront — huge bundle import HeavyChartComponent from './HeavyChart' ✅ Only loads when needed const HeavyChart = React.lazy(() => import('./HeavyChart'))

Tree Shaking:

❌ Imports entire lodash (70kb) import _ from 'lodash' ✅ Only imports what you use (2kb) import debounce from 'lodash/debounce'

CDN Impact:

Without CDN: User in Mumbai → hits server in US → 200ms With CDN: User in Mumbai → hits edge in Mumbai → 10ms
⚙️ Layer 2 — Parse & Run (Deep Dive)

Route-based code splitting:

// Only load each page's JS when user navigates there const HomePage = React.lazy(() => import('./pages/Home')) const ProductPage = React.lazy(() => import('./pages/Product')) const CheckoutPage = React.lazy(() => import('./pages/Checkout'))

Defer non-critical scripts:

❌ Blocks HTML parsing <script src="analytics.js"></script> ✅ Loads after HTML is parsed <script src="analytics.js" defer></script>
💡 Third party scripts (analytics, chat, ads) should always be deferred or async. They're not critical to first render.
🎨 Layer 3 — Render (Deep Dive)

Virtualization:

❌ Rendering 10,000 items in DOM → browser creates 10,000 DOM nodes → massive memory, slow scroll ✅ react-window / react-virtual → only renders ~10-15 visible items → recycles DOM nodes on scroll → feels instant even with millions of items

CSS transforms over position:

❌ Triggers layout + paint (expensive) .moving { left: 100px; top: 50px; } ✅ Only triggers composite (GPU, cheap) .moving { transform: translate(100px, 50px); }

Avoid layout thrash:

❌ Read + write mixed — triggers recalc every iteration elements.forEach(el => { el.style.width = container.offsetWidth + 'px' }) ✅ Batch reads then writes const width = container.offsetWidth // read once elements.forEach(el => { el.style.width = width + 'px' // write only })
✨ Layer 4 — Perceived Performance (Deep Dive)

Optimistic Updates (most important):

❌ Wait for API — user feels 300ms delay await likePost(postId) setLiked(true) ✅ Update UI first — feels instant setLiked(true) // immediate feedback await likePost(postId) .catch(() => { setLiked(false) // rollback if API fails showError() })

Skeleton screens vs blank loading:

❌ Blank white page → user thinks it's broken ✅ Skeleton UI → user sees structure, feels progress Shows layout immediately, content fills in as it loads
Perceived performance is the most underrated layer. Users don't measure milliseconds — they measure frustration. A skeleton screen on a 500ms load feels faster than a blank screen on a 300ms load.
Vitals

Core Web Vitals

📊 The 3 Metrics That Matter
LCP
Largest Contentful Paint
< 2.5 seconds

How long until main content is visible on screen

INP
Interaction to Next Paint
< 200ms

How fast page responds to user clicks and input

CLS
Cumulative Layout Shift
< 0.1

Does the page jump around while loading

MetricMain CausesFixes
LCP Slow server, render-blocking JS, large hero image SSR/SSG, CDN, preload hero image, WebP format
INP Too much JS on main thread, heavy event handlers Code split, reduce JS, web workers for heavy tasks
CLS Images/ads without dimensions, late-injected content Always set width + height on images and ad slots
🖼️ Image Optimization — High Impact, Easy Wins
❌ Basic image — no optimization <img src="hero.jpg" /> // 2MB PNG, any size, blocks CLS ✅ Fully optimized image <img src="hero.webp" // WebP = 30% smaller than JPG srcset="hero-400.webp 400w, hero-800.webp 800w" // right size per screen loading="lazy" // don't load until near viewport width="800" height="600" // prevents CLS layout shift />

4 fixes in one image tag: WebP + srcset + lazy loading + dimensions

QuestionYour AnswerCorrect AnswerVerdict

Like button instant feel FID/INP metric Optimistic update — flip liked state immediately, sync to API in background, rollback on failure ❌ Wrong layer

🧪 Netflix Movie Browsing Page — Hero + 500 thumbnails

Complete 4-Layer Answer

Network

Serve all images from CDN. Convert thumbnails to WebP. Set explicit dimensions to prevent CLS on hero banner.

Parse & Run

Lazy load the video player and movie detail modal — they're heavy and only needed when user clicks a title.

Render

Virtualize horizontal movie rows with react-window. 500+ thumbnails shouldn't all live in the DOM.

Perceived

Show skeleton cards while thumbnails load. Blur-up placeholder for hero banner image.

🧪 Google Maps Frontend — Markers, search, routes, traffic

Complete 4-Layer Answer

Network

Serve map tiles from geographically close CDN nodes. Cache tiles aggressively — they rarely change.

Parse & Run

Lazy load Street View, route calculator panel, and satellite mode — most users never use them on first load.

Render

Only render markers visible in current viewport. As user pans, load new markers and discard off-screen ones. Same concept as react-window but for map coordinates.

Perceived

Show skeleton for search results instantly. Draw optimistic route line immediately while exact calculation completes in background.

⚠️ Common mistake on Maps: Saying "SSR/CSR" for Parse & Run. That's rendering strategy (Day 1). Parse & Run = JS bundle cost only.
🗂️ Performance Cheat Sheet
Layer 1 — Network CDN for all assets → serve from edge, near the user WebP format → 30% smaller than JPG Code splitting → React.lazy() + dynamic import Tree shaking → import { x } not import * HTTP/2 → parallel requests Layer 2 — Parse & Run Route-based splitting → lazy load each page separately Defer 3rd party scripts → <script defer> Lazy load heavy components → player, modal, map, editor Layer 3 — Render Virtualize long lists → react-window / react-virtual CSS transforms → transform: translate() not left/top Batch DOM reads/writes → avoid layout thrash will-change: transform → hint browser to use GPU layer Layer 4 — Perceived Skeleton screens → show structure before data Optimistic updates → update UI first, sync after Progressive loading → blur-up images, partial content Prefetch on hover → preload next page before click
💬 What a Staff-Level Performance Answer Sounds Like
"I think about performance in 4 layers. First network — am I sending too much? I'd code-split by route and use WebP images from a CDN. Second, parse cost — defer non-critical scripts and lazy-load heavy components like the video player. Third, render — virtualize any list over 100 items and use CSS transforms for animations to stay on the GPU. Fourth and most underrated — perceived performance. Skeleton screens and optimistic updates make an app feel instant even when the network is slow."

That answer covers all 4 layers with concrete examples. Sounds senior immediately. ✅

🎯 The One Habit to Lock In

Every performance answer — lead with the layer name first:

"For network I'd..." "For parse cost I'd..." "For rendering I'd..." "For perceived performance I'd..."

This structure alone sounds more senior than 90% of candidates — even before you get to the content.
